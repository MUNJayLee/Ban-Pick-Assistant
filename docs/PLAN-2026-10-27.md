## 一、红方 ban 识别（待修）

### 问题
用户确认：**红方 ban 确实没识别到**（不是帧没抓到）。

### 已掌握的线索
| 数据 | 结果 |
|---|---|
| 蓝方 ban 识别 | ✅ 5/5 全对（庄周/元流之子/王维/哪吒/海月） |
| 红方 ban 坐标 | 理论镜像 `1 - BAN_X_RATIOS`，真机截图曾验证过（pick 完成图上红方 5 个能识别） |
| 红方 ban std | 抓到帧里红方全是 6-8（空位特征）— 但那是「红方还没 ban」的帧 |

### 根因假设（按概率排序）
1. **红方 ban 位出现时机**：红方 ban 可能只在很短时间内显示（用户说没识别到，说明确实 ban 了）
2. **坐标镜像偏差**：红方位置可能不是严格镜像（右侧布局可能有偏移）
3. **遮挡**：红方 ban 位可能被「Ban 确认动画/头像」遮挡

### 实施方案
```
Step 1  采集红方 ban 帧（每次 ban 变化存帧已加）
Step 2  测量红方 ban 位精确坐标（HoughCircles + 人工核对）
Step 3  验证 std/ORB（对比蓝方成功的参数）
Step 4  调整坐标/阈值
Step 5  真机验证
```

### 风险
- 明天需要再打一局采集数据
- 如果红方 ban 位和蓝方差异大，可能需要单独的坐标表

## 二、记录详情页可编辑（待做）

### 现状
- `bpRecordStore.updateRecord(id, updates)` **已支持全字段更新** ✓
- 记录页（`BpRecords.tsx`，572 行）只有「展开/删除」，**没有编辑入口**
- 用户反馈：记录错了改不了

### 方案

#### UI 改动
```
记录卡片（展开状态）
  ├── 现有内容（双方阵容 / Ban / 结果 / 评分）
  └── [新增] 底部按钮行：「编辑」按钮
        ↓ 点击弹窗
  记录编辑弹窗（RecordEditModal）
  ├── 蓝方 picks（5 个英雄选择器）
  ├── 红方 picks（5 个）
  ├── 蓝方 bans（5 个）
  ├── 红方 bans（5 个）
  ├── 我的英雄（搜索选择）
  ├── 对局结果（赢/输/未定）
  ├── 评分（0~16）+ MVP + 奖牌
  ├── 备注（textarea）
  └── [取消] [保存]
        ↓
  updateRecord(id, updates) → 自动同步 Supabase
```

#### 技术要点
| 点 | 方案 |
|---|---|
| 英雄选择器 | 复用 `HeroSearch` 组件，或者写简化版（输入框 + 下拉） |
| 空位处理 | 允许「空」= 从记录里移除 |
| 校验 | 我的英雄必须在「我方 picks」里（复用之前的校验逻辑） |
| 保存 | `updateRecord` 已有 Supabase 同步（`syncService.uploadBpRecord`） |

#### 工作量
- `RecordEditModal.tsx`：约 250 行
- `BpRecords.tsx`：加「编辑」按钮 + 状态（约 30 行）
- **合计约 1~1.5 小时**

### 设计决策（待确认）
1. **编辑方式**：
   - A. 弹窗内编辑（推荐，简单）
   - B. 跳转到 BP 页面加载该记录（复杂，但可视化好）

## 三、功能测试子 agent 设计

### 目标
让子 agent **独立完成功能测试**，输出报告，不占用主 agent 上下文。

### 子 agent 职责

#### 1. 前端功能测试（浏览器自动化）
```
测试项：
- 各页面渲染（BP 模拟 / 数据看板 / 记录）
- 英雄点击（选 ban / 选 pick）
- 阵营切换（数据保留验证）
- 记录展开/删除/编辑
- 推荐面板分组显示
- 设备配置弹窗（WiFi 连接 UI）
- 响应式（1440 / 1920 宽）

方法：REA browser automation（CDP）
  - 启动 headless Edge + CDP
  - 点击/截图/检查 DOM
  - 输出：通过/失败 + 截图路径
```

#### 2. API 接口测试（Python）
```
测试项：
- 13 个端点（health/devices/state/phase/capture/recognize/once/bp/start/stop/data/sync/heroes/device/select/connect/disconnect）
- 正常输入
- 异常输入（空 IP、无效设备）
- 错误处理

方法：requests + 边界用例
```

#### 3. 识别函数测试（Python）
```
测试项：
- detect_phase（样本图 10 张）
- recognize_bans（真机截图 6 张）
- recognize_picks（真机截图 6 张）
- detect_player_floor（样本 4 张）
- detect_game_result（结算样本 2 张）

方法：用 samples/ 目录的样本，比对期望值
```

#### 4. 输出报告
```
docs/TEST_REPORT_<date>.md
  ├── 测试概况（通过/失败统计）
  ├── 失败项详情（复现步骤 + 截图）
  └── 建议修复优先级
```

### 子 agent 的边界（重要）
| 允许 | 不允许 |
|---|---|
| 读写测试报告 | 修改源码 |
| 启动 headless 浏览器 | 重启正式服务（8900/5173） |
| 调用 API（只读/无害） | 修改数据（记录/配置） |
| 截图 | 连接真机（避免干扰用户） |

### 子 agent 的 prompt 设计

```
你是「功能测试员」，负责独立测试王者BP助手 v3.0，输出测试报告。

## 测试范围
1. 前端（http://localhost:5173/）：页面渲染、交互、记录编辑
2. API（http://127.0.0.1:8900/）：13 个端点
3. 识别函数（scripts/live_recognize.py）：用 samples/ 样本

## 工具
- REA browser automation（CDP endpoint: 启动 headless Edge）
- Python（requests / opencv / 直接 import 识别模块）
- 文件读写（测试报告）

## 边界（必须遵守）
- 不要修改任何源码
- 不要重启 8900/5173 服务
- 不要连接真机（adb）
- 不要修改记录/配置数据

## 输出
docs/TEST_REPORT_<YYYY-MM-DD>.md：
- 每项测试：通过/失败
- 失败项：复现步骤 + 截图路径 + 预期 vs 实际
- 按严重程度排序
```

### 什么时候跑
- 每次大改动后（如记录编辑完成后）
- 用户测试前（回归测试）
- 可以后台跑（不阻塞主 agent）
